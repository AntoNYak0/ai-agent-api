В основе этих механик лежит ключевое свойство стандарта Permit2: клиент подписывает разрешение не на один конкретный платёж, а на право сервера списывать средства с его адреса в рамках заданного лимита (amount) и до истечения срока действия (expiration). Это открывает дорогу к нескольким сценариям, которые я подробно опишу ниже.
⏳ Сценарий 1: Поэтапное списание за длинные цепочки операций

Представьте агента, который запускает у вас сложный, многошаговый бизнес-процесс: сначала нужно подобрать ключевые слова в вашей БД, затем сгенерировать три варианта текста, а потом проверить лучший из них на антиплагиат. Платить сразу за всё целиком — рискованно (вдруг процесс упадёт на середине), да и точную цену заранее назвать нельзя.

Протокол x402 позволяет вашему серверу взимать плату итеративно, по мере выполнения каждого дорогостоящего этапа.
Как это реализовать (детальный алгоритм)

    Начальный запрос: Агент стучится на ваш эндпоинт /api/start-complex-job.

    402 с upto: Вы отвечаете 402, указывая схему upto с максимальной ценой, которая покрывает самый дорогой из возможных сценариев (например, $1.50). Это ваш страховочный лимит.

    Первичная верификация: Агент присылает свой PAYMENT-SIGNATURE. Ваш сервер (через фасилитатора) выполняет verifyPayment. Убедитесь, что лимита достаточно и подпись валидна. Сохраните объект paymentData в сессии или базе данных — он вам понадобится для последующих списаний.

    Этап 1: Семантический поиск. Вы выполняете дорогостоящий запрос к векторной базе данных. Операция стоила $0.15.

        Вызываете settlePayment, передав в price значение $0.15.

        Фасилитатор списывает $0.15.

        Вы возвращаете агенту ответ с результатами первого этапа и добавляете заголовок PAYMENT-RESPONSE, подтверждающий списание. Разрешение агента всё ещё действительно на оставшиеся $1.35.

    Этап 2: Генерация текста. Агент присылает результаты этапа 1 и просит сгенерировать варианты. Вы генерируете 3 варианта, потратив токенов на $0.40.

        Вы снова вызываете settlePayment с тем же, ранее сохранённым paymentData, но с ценой $0.40.

        Фасилитатор списывает ещё $0.40. Остаток лимита: $0.95.

    Этап 3: Проверка орфографии и антиплагиат. Процесс стоит $0.25. Вы списываете и эту сумму.

    Завершение: Выполнив всю работу и получив все микроплатежи, вы возвращаете агенту финальный результат.

Такой подход делает бизнес-модель честной и гибкой: клиент не рискует всей суммой сразу, а вы получаете деньги за каждый успешный этап работы.
🛡️ Сценарий 2: Продвинутая валидация и снижение бизнес-рисков

Помимо стандартной проверки подписи и суммы, вы можете добавить кастомные проверки на стороне сервера, чтобы защитить себя от недобросовестных клиентов или ошибок. verifyPayment — идеальное место для такого шлюза.
Примеры кастомных проверок:

    Баланс и лимиты: Проверьте, что лимит, указанный клиентом в maxPrice, покрывает минимально возможную стоимость операции (minPrice), которую вы установили.

    Репутация клиента: Интегрируйте реестр репутации (например, на базе ERC-8004). Перед тем как тратить дорогие GPU-ресурсы, ваш сервер может асинхронно проверить репутацию кошелька клиента и понизить для него приоритет или вовсе отказать, если за ним числятся попытки атак или неплатежи.

    Лимиты по IP/ASN: Отклоняйте запросы от IP-адресов хостинг-провайдеров или TOR-выходных узлов, которые часто используются для автоматизированных атак.

javascript

// Пример функции-обертки для проверки репутации во время verifyPayment
async function strictVerifyAndSettle(paymentArgs) {
  // Стандартная проверка
  const verify = await verifyPayment(paymentArgs);
  if (verify.status !== 200) return reject(verify);

  // Асинхронная проверка репутации кошелька клиента
  const reputation = await checkReputation(paymentArgs.paymentData.sender);
  if (reputation.riskScore > 70) {
    return { status: 403, body: { error: "High-risk wallet. Access denied." } };
  }

  // Если всё хорошо, продолжаем
  return true;
}

🔗 Сценарий 3: Паттерн "Шлюз" для доступа к API без API-ключей

Этот сценарий идеально подходит, если вы хотите продавать доступ не просто к данным, а к целым внешним API или сервисам, не раздавая при этом секретные ключи.

Представьте, что у вас есть проприетарный алгоритм обработки изображений. Вы не хотите раскрывать его код, но хотите продавать к нему доступ. x402 позволяет вам стать посредником: вы получаете платёж от агента и из своих средств оплачиваете использование алгоритма, запуская его в защищённой среде (например, Trusted Execution Environment, TEE).
Пошаговая архитектура:

    Агент -> Ваш Публичный API: Агент отправляет изображение на ваш эндпоинт /api/anonymize-image.

    Ваш API -> Агент: Возвращает 402 Payment Required с ценой $0.50.

    Агент -> Ваш API: Агент повторяет запрос с PAYMENT-SIGNATURE и изображением.

    Ваш API -> Фасилитатор: Вы проверяете платёж через verifyPayment.

    Ваш API -> Проприетарный Модуль (внутри TEE): Если платёж прошёл верификацию, вы отправляете изображение в защищённый анклав. Ключи API от внешнего сервиса "зашиты" в этом анклаве и никогда не покидают его. Модуль внутри TEE выполняет работу и возвращает результат.

    Ваш API -> Фасилитатор: Вызывается settlePayment. Средства от агента поступают на ваш счёт.

    Ваш API -> Агент: Агенту возвращается обработанное изображение.

В этой схеме вы становитесь "продавцом доступа к возможностям". Агент платит только вам, не зная и не имея доступа к тому, как именно вы решаете его задачу. Это мощная модель для монетизации сложных B2B-интеграций.
💡 Сценарий 4: Pay-as-you-go для потоковых данных (набросок)

Если ваш сервис предоставляет непрерывный поток данных (например, аудио с микрофона умного города или потоковое LLM-взаимодействие), вы можете комбинировать схему upto с техникой HTTP Long Polling или Server-Sent Events (SSE).

Механика следующая:

    Клиент авторизует лимит в $1.00.

    Сервер открывает SSE-соединение и начинает слать данные.

    Каждые 10 секунд или после отправки определённого объёма данных сервер в фоновом режиме вызывает settlePayment на микро-сумму (например, $0.005 за пакет данных), используя исходное разрешение клиента.

    Когда накопленная сумма списаний достигает лимита, сервер отправляет клиенту новое требование 402 прямо в потоке SSE и приостанавливает отправку данных до получения новой подписи.

Этот подход превращает любой API в коммунальную услугу с поминутной тарификацией, что является вершиной модели "плати только за то, что используешь".
