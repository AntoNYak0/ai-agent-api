Пошаговая инструкция для продавца

Вот как выглядит полный цикл обработки запроса с динамической ценой на вашем сервере:

    Клиент делает запрос. Покупатель обращается к вашему платному эндпоинту без заголовка PAYMENT-SIGNATURE.

    Сервер требует оплату с максимальной ценой. Вы отвечаете HTTP-статусом 402 Payment Required. В ответе и заголовке PAYMENT-REQUIRED вы указываете схему upto, а в поле цены — максимально возможную стоимость операции. Например, $0.10.

    Клиент авторизует максимум. Покупатель, видя флаг upto, понимает, что это не точная цена, а лимит. Он подписывает транзакцию (Permit2) на сумму до $0.10 и отправляет повторный запрос с заголовком PAYMENT-SIGNATURE .

    Сервер верифицирует платеж. Вызывается функция verifyPayment. Сервер проверяет, что подпись клиента валидна, что срок ее действия не истек, и что баланс/разрешение покрывают максимальную сумму. Это критически важно сделать до выполнения дорогостоящей работы, чтобы не потратить ресурсы на несостоятельного клиента . Если верификация не прошла, вы сразу возвращаете ошибку.

    Сервер выполняет работу. Вы запускаете свой ИИ-инференс или другую ресурсоемкую задачу. В процессе вы замеряете фактическое потребление ресурсов: количество токенов, затраченное время CPU/GPU и т.д.

    Сервер рассчитывает итоговую цену. После получения результата вы вычисляете финальную стоимость. Например, если у вас цена 0.00001затокен,амодельсгенерировала150токенов,тоитоговаяценасоставит0.00001затокен,амодельсгенерировала150токенов,тоитоговаяценасоставит0.0015.

    Сервер списывает финальную сумму. Вызывается функция settlePayment, в которую передается уже не максимальная, а рассчитанная итоговая цена. Фасилитатор проводит транзакцию в блокчейне именно на эту сумму. Платежное разрешение клиента при этом остается валидным для дальнейших списаний в рамках того же лимита до истечения срока действия .

    Сервер возвращает результат. Вы отправляете клиенту ответ с данными и заголовком PAYMENT-RESPONSE, подтверждающим успешное списание.

Вот обобщенный пример того, как это выглядит в коде, основанный на документации :
javascript

// Настройка параметров платежа
const paymentArgs = {
  resourceUrl: "https://api.example.com/ai-inference",
  method: "POST",
  paymentData, // данные из PAYMENT-SIGNATURE клиента
  payTo: "0xYourMerchantAddress",
  network: arbitrum, // или другая EVM-сеть
  scheme: "upto", // Ключевой параметр для динамической цены
  price: "$0.10", // Максимальная цена, которую клиент готов заплатить
  minPrice: "$0.01", // Минимальная граница для валидации (опционально)
  facilitator: myFacilitator,
};

// Шаг 1: Верификация ДО выполнения работы
const verifyResult = await verifyPayment(paymentArgs);
if (verifyResult.status !== 200) {
  // Если клиент недействителен, сразу отказываем
  return Response.json(verifyResult.responseBody, {
    status: verifyResult.status,
    headers: verifyResult.responseHeaders,
  });
}

// Шаг 2: Выполнение ресурсоемкой задачи
const { result, tokensUsed, computeTime } = await performAIInference(query);

// Шаг 3: Расчет фактической стоимости
const pricePerToken = 0.00001; // $0.00001 за токен
const finalPrice = tokensUsed * pricePerToken;

// Шаг 4: Списание итоговой суммы
const settleResult = await settlePayment({
  ...paymentArgs,
  price: `$${finalPrice}`, // Передаем фактическую цену
});

// Шаг 5: Возврат результата клиенту
return Response.json({
  success: true,
  data: result,
  usage: { tokens: tokensUsed, cost: finalPrice }
});

Важный нюанс, который следует учитывать при такой реализации: вызовы verifyPayment и settlePayment можно повторять несколько раз, используя одно и то же paymentData от клиента, пока срок его действия не истек . Это открывает возможность взимать плату поэтапно за длинные цепочки операций.
